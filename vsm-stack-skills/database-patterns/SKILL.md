# Database Patterns

Universal database design and usage patterns. Language-agnostic.

## Schema Design
- Normalize until you have a reason to denormalize
- Use appropriate constraints (NOT NULL, UNIQUE, FOREIGN KEY)
- Version-control all schema changes via migrations

## Query Performance
- N+1 prevention: eager loading, batching, or JOINs
- Index on frequently queried columns
- Avoid SELECT * in production queries

## Connection Management
- Connection factory (avoid module-level instantiation — see `[language]-pitfalls`)
- Connection pooling for production
- Separate read and write connections if scale requires

## Migrations
- Migration files must be reversible
- Test migrations against production-like data volumes
- Never modify existing migration files after deployment

## Rule: Alembic Async Migration Traps

**Status**: Active (FB29-sourced, theoretical — awaiting validation in FB33+)
**Severity**: BLOCKER
**Applies to**: vsm_backend_coder, vsm_backend_tester, vsm_coordinator

When using `asyncpg` with Alembic, the default `env.py` generated by `alembic init` is synchronous. Running async migrations with a sync engine against an async PostgreSQL driver causes `asyncpg.exceptions._base.InterfaceError` or silent connection deadlocks.

**Correct pattern**:
```python
# alembic/env.py
from sqlalchemy.ext.asyncio import create_async_engine
import asyncio

config = context.config
target_metadata = Base.metadata

async def run_migrations_online():
    connectable = create_async_engine(config.get_main_option("sqlalchemy.url"))
    async with connectable.connect() as connection:
        await connection.run_sync(do_run_migrations)
    await connectable.dispose()

def do_run_migrations(connection):
    context.configure(connection=connection, target_metadata=target_metadata)
    with context.begin_transaction():
        context.run_migrations()

if context.is_offline_mode():
    context.configure(url=config.get_main_option("sqlalchemy.url"))
    with context.begin_transaction():
        context.run_migrations()
else:
    asyncio.run(run_migrations_online())
```

**Incorrect pattern** (BLOCKER):
```python
# Sync engine with asyncpg URL — connection hangs or crashes
engine = create_engine("postgresql+asyncpg://...")  # WRONG
default_connection = engine.connect()
context.configure(connection=default_connection)
```

**Prevention rules**:
1. If the project uses `asyncpg` or `aiosqlite`, Alembic `env.py` MUST use `create_async_engine` and `connection.run_sync()`.
2. Backend tester MUST verify `alembic upgrade head` succeeds in CI before deployment.
3. Never mix sync `create_engine` with an async driver URL.

**Source**: FB29 `alembic/env.py` used sync engine; migrations hung on async database. Fixed by converting to async engine pattern. Full validation pending dedicated gym experiment.

## Rule: PostgreSQL-Specific Index Naming Conventions

**Status**: Active (theoretical — awaiting validation)
**Severity**: LOW (productivity pattern)
**Applies to**: vsm_backend_coder, vsm_auditor

Alembic auto-generates index names like `ix_table_column` which are fine, but manually created indexes should follow a consistent convention to prevent name collisions and ease debugging.

**Naming convention**:
| Index Type | Pattern | Example |
|---|---|---|
| Standard B-tree | `ix_{table}_{column}` | `ix_users_email` |
| Unique | `uq_{table}_{column}` | `uq_users_email` |
| Composite | `ix_{table}_{col1}_{col2}` | `ix_orders_user_id_status` |
| Partial (filtered) | `ix_{table}_{column}_{filter}` | `ix_tasks_status_pending` |
| GIN/GIST | `ix_{table}_{column}_gin` | `ix_articles_search_gin` |

**Prevention rules**:
1. Explicitly name every index created in a migration; never rely on Alembic auto-naming for manually added indexes.
2. Auditor MUST flag unnamed `op.create_index()` calls as ISSUE.
3. Index names MUST be ≤63 characters (PostgreSQL identifier limit).

**Source**: Theoretical pattern derived from PostgreSQL documentation and schema review best practices. No direct build failure yet attributed to this, but unnamed indexes complicate production debugging.

## Rule: Connection Pool Sizing for FastAPI / Async Workloads

**Status**: Active (theoretical — awaiting validation)
**Severity**: MEDIUM (performance / availability)
**Applies to**: vsm_backend_coder, vsm_devops_coder, vsm_coordinator

FastAPI with Uvicorn defaults to multiple worker processes. Each worker maintains its own SQLAlchemy connection pool. Default pool settings (`pool_size=5`, `max_overflow=10`) can exhaust the PostgreSQL `max_connections` limit under moderate load.

**Sizing formula**:
```
total_db_connections = (uvicorn_workers) * (pool_size + max_overflow)
# Must be ≤ PostgreSQL max_connections (default 100)
```

**Correct pattern**:
```python
# For a 4-worker Uvicorn setup with PG max_connections=100
engine = create_async_engine(
    DATABASE_URL,
    pool_size=10,        # 4 * 10 = 40 baseline
    max_overflow=5,      # 4 * 5 = 20 burst = 60 total
    pool_pre_ping=True,  # Validate connection health before use
    pool_recycle=3600,   # Recycle connections after 1 hour
)
```

**Incorrect pattern** (MEDIUM):
```python
# Default pool_size=5, max_overflow=10 with 8 workers = 120 connections
engine = create_async_engine(DATABASE_URL)  # Uses defaults; may exceed PG limit
```

**Prevention rules**:
1. Backend coder MUST document `pool_size` and `max_overflow` in `config.py` comments with the total connection math.
2. DevOps coder MUST set PostgreSQL `max_connections` in `docker-compose.yml` or k8s config to match expected total.
3. Coordinator MUST verify `docker-compose.yml` `POSTGRES_MAX_CONNECTIONS` ≥ calculated total + overhead (e.g., +20 for migrations/admin).

**Source**: Theoretical — derived from SQLAlchemy and PostgreSQL documentation. No build failure directly attributed yet, but connection exhaustion is a known production risk for async FastAPI stacks.

## Rule: SQLite vs PostgreSQL Column Type Compatibility

**Status**: Active (FB30-sourced)
**Severity**: BLOCKER
**Applies to**: vsm_backend_coder, vsm_backend_tester, vsm_auditor

When tests use SQLite but production uses PostgreSQL, several column type features are incompatible. Using PostgreSQL-specific features in models breaks test `Base.metadata.create_all()` or causes runtime failures in SQLite.

**Incompatible features**:
| PostgreSQL Feature | SQLite Equivalent | Risk |
|---|---|---|
| `server_default=sa.text("gen_random_uuid()")` | `default=uuid.uuid4` | SQLite has no `gen_random_uuid()` |
| `sa.UUID` columns | `sa.String(36)` or monkeypatch | Needs bind processor (see `testing-patterns`) |
| `sa.Numeric(precision, scale)` | `sa.REAL` or `sa.NUMERIC` | Precision loss; use `Decimal` carefully |
| `server_default=sa.text("now()")` | `default=datetime.utcnow` | SQLite `now()` behaves differently in some drivers |
| `CHECK` constraints with `sa.Boolean` | `sa.Integer` under the hood | Boolean values may store as 0/1 |

**Correct pattern**:
```python
from uuid import uuid4
import sqlalchemy as sa

class User(Base):
    __tablename__ = "users"
    # Portable default — works on both SQLite and PostgreSQL
    id: Mapped[uuid.UUID] = mapped_column(
        sa.Uuid(as_uuid=True),
        primary_key=True,
        default=uuid4,  # ✅ Python-side default, portable
    )
    created_at: Mapped[datetime] = mapped_column(
        sa.DateTime(timezone=True),
        default=datetime.utcnow,  # ✅ Portable
    )
```

**Incorrect pattern** (BLOCKER):
```python
class User(Base):
    id = mapped_column(
        sa.Uuid(as_uuid=True),
        primary_key=True,
        server_default=sa.text("gen_random_uuid()"),  # ❌ Fails on SQLite
    )
```

**Prevention rules**:
1. If tests use SQLite, NEVER use `server_default=sa.text("gen_random_uuid()")`. Use `default=uuid4` instead.
2. If `server_default` is required for PostgreSQL production, wrap it in a conditional:
   ```python
   from os import environ
   if "sqlite" in environ.get("DATABASE_URL", "").lower():
       id_col = mapped_column(sa.Uuid, primary_key=True, default=uuid4)
   else:
       id_col = mapped_column(sa.Uuid, primary_key=True, server_default=sa.text("gen_random_uuid()"))
   ```
3. Backend tester MUST verify `Base.metadata.create_all()` succeeds with the test DATABASE_URL before running any tests.
4. Coordinator MUST check that `docker-compose.yml` PostgreSQL image and test SQLite both accept the same model definitions.

**Source**: FB30 `models.py` used `server_default=sa.text("gen_random_uuid()")`. SQLite tests crashed during `create_all()` with `OperationalError: no such function: gen_random_uuid`. Fixed by switching to `default=uuid4`. Mutation ID: M-FB30-4.
